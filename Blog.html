Learning to Code in the Age of AI

Learning to Code in the Age of AI: My Journey So Far

I think one of the weirdest times to decide you want to seriously learn programming is probably right now.

Every few weeks there is another AI model coming out, another video saying software engineering is dead, another video saying actually software engineering is more important than ever, and then another guy on Twitter saying he built an entire startup in a weekend without knowing how to code.

So naturally I decided this was the perfect time to learn how to code.

I started this journey with a pretty simple goal. I want to become good enough at programming that I can actually build things that I have in my head.

Not just follow tutorials.

Not just copy somebody else's calculator from YouTube.

Actually have an idea, open my computer, stare at a blank screen for probably an unreasonable amount of time, and eventually turn that idea into something real.

I also want to eventually work professionally as a software developer. That is obviously the bigger goal. But weirdly enough, the more I learn, the less I think getting a job should be the thing I'm thinking about every single day.

Right now I mostly just want to become dangerous enough with a computer that when I have an idea, my first thought isn't "I wish somebody would make this."

I want my first thought to be:

How would I build this?

And AI has made that journey very strange.

Where I Started

I didn't start completely unfamiliar with computers.

I've always been somebody who likes figuring things out. I've messed around with servers, websites, games, computers, troubleshooting things, and a bunch of random technical stuff over the years.

But there is a massive difference between being "good with computers" and actually understanding programming.

That became obvious extremely fast.

When you first look at code it honestly looks kind of ridiculous. 

if user_answer.lower() == "yes":
        print("Hello")

Looks incredibly simple to me now.

But when you're brand new there are like six different questions inside those two lines.

Why is there a colon?

Why are there parentheses?

Why does .lower() have a dot?

Why does print need parentheses?

Why are there quotation marks around yes?

Why is the second line moved over?

What happens if I don't move it over?

And then you remove one tiny character and Python basically tells you:

"Absolutely not."

Sometimes it tells you why.

Sometimes it tells you something that technically explains why, but feels like it was written by a wizard who hates you.

That was basically the beginning.

Python Was My First Real Step

Python was the first language where I actually tried to understand what I was doing instead of just copying code.

At the beginning I was learning the extremely basic stuff.

Variables. Strings. Integers. Floats. User input. Type casting. If statements. Else statements. Loops. Lists. Functions.

All of the things that experienced programmers probably don't even consciously think about anymore.

One thing I noticed pretty quickly though was that I hated just watching somebody type code.

It felt productive, because technically I was "learning programming," but I realized I could watch somebody build something and understand basically everything they're saying, then open a blank Python file myself and suddenly my brain would be empty.

That was probably one of the first important lessons I learned.

Recognizing code isn't the same thing as knowing how to write code.

It's kind of like watching someone play basketball and thinking you understand what they're doing.

Yeah.

You do understand it.

But that doesn't mean you can do it.

So I started doing something that has probably helped me more than anything else so far.

I started trying to beat the tutorial.

Trying to Beat the Tutorial

Basically, whenever a tutorial says:

"Now we're going to build a temperature converter."

I pause the video.

Then I try building it myself first.

Usually badly.

Sometimes very badly.

But that's kind of the point.

One of the first projects where I really noticed a difference was a temperature converter.

The tutorial was going to show how to convert Fahrenheit and Celsius.

Before watching it, I tried making my own.

Then I thought, well why only Fahrenheit and Celsius?

So I added Kelvin.

That meant suddenly instead of just Celsius to Fahrenheit and Fahrenheit to Celsius, I had to think about Celsius to Kelvin, Fahrenheit to Kelvin, Kelvin to Celsius, Kelvin to Fahrenheit, and everything in between.

This was still an incredibly basic program.

I'm not pretending I invented Facebook here.

But something important happened while I was making it.

I had a problem that the tutorial wasn't directly solving anymore.

I had to figure it out.

And that meant Googling things. Testing formulas. Making mistakes. Running the program. Getting an error. Changing something. Running it again. Realizing it technically works but there's another situation I didn't account for. Changing it again.

That process felt completely different than just following along.

For the first time I wasn't learning programming as information.

I was actually programming.

The First Thing That Really Clicked

One of the things I'm slowly understanding is that programming isn't actually about remembering code.

This sounds extremely obvious when I write it down.

But I genuinely didn't understand this at first.

I thought becoming a programmer basically meant slowly memorizing more and more syntax until eventually you knew enough commands to build software.

That's not really what seems to be happening.

I'm starting to think programming is much closer to learning how to break problems apart.

The syntax matters obviously.

I need to know what an if statement is.

I need to understand loops.

I need to understand variables.

But knowing that a hammer exists doesn't tell you how to build a house.

The interesting part is deciding where the hammer needs to be used.

For example, I made a little student grade program.

The idea was simple.

Ask for a student's name.

Ask for their grade.

Store the information.

Repeat until the user says they're done.

Then eventually calculate things like the average grade, highest grade, lowest grade, etc.

Again, nothing revolutionary.

But suddenly I needed several concepts working together.

I needed a loop because I didn't know how many students would be entered.

I needed lists because I needed somewhere to store the data.

I needed conditions because grades below 0 or above 100 shouldn't be accepted.

I needed to convert the input into a number because Python gives input back as a string.

Then I had to think about what happens if somebody enters something stupid.

What if they type 150?

What if they type -12?

What if they type "banana"?

What if they type "done"?

What if they type "Done"?

What if they type "DONE"?

Every answer creates another question.

And I'm realizing that's basically software development.

The Humbling Experience of Debugging

Debugging has probably taught me more than anything else.

It also occasionally makes me want to throw my computer into the Saskatchewan River.

There is a particular type of anger that happens when you've been looking at your code for ten minutes and cannot understand why it doesn't work.

Then you finally find the problem.

You wrote = instead of ==.

Or you forgot a colon.

Or something is indented one level too far.

Or you created a variable inside one branch of an if statement and then tried using it later when that branch never ran.

The computer is completely correct.

Which honestly makes it worse.

I've started realizing that when my program doesn't work, randomly changing things usually isn't helpful.

Instead I'm trying to get into the habit of asking:

What exactly did I expect to happen?

Then:

What actually happened?

Then:

At what point did those two things become different?

That sounds almost stupidly simple but it changes debugging completely.

Instead of staring at 60 lines of code thinking "WHY DOESN'T THIS WORK", I can start narrowing the problem down.

Is the input correct? Print it.

Is the variable the type I think it is? Check it.

Did this condition actually run? Put a print statement inside it.

What value does this variable have right here? Print it.

I'm basically learning to interrogate my own program.

And usually somewhere during that interrogation I discover that the murderer was me.

Then I Started Learning HTML

Moving from Python to HTML was weird.

Because technically HTML isn't really programming in the same way Python is.

There isn't much logic happening.

You're describing structure.

At first HTML felt almost ridiculously easy compared to Python.

You write: 

<h1>Hello</h1>

and congratulations.

You have a giant Hello.

You write: 

<p>This is my paragraph.</p>

and now there's a paragraph.

You put an image tag in.

There's an image.

For approximately 20 minutes I thought web development might be easy.

Then CSS arrived.

CSS Is Black Magic Pretending to Be Design

CSS is probably the funniest thing I've learned so far.

Because when it works, I feel like I understand it completely.

Then something refuses to move 30 pixels to the right and suddenly I am questioning everything I've learned.

I've been building my portfolio website while learning HTML and CSS.

The website is called It's All Subjective.

I wanted it to actually look like something I would make instead of one of those tutorial portfolios where everything is white, there's a picture of somebody smiling with their arms crossed, and underneath it says:

"Hi, I'm John. I'm a passionate Full Stack Developer."

I wanted mine to have an identity.

Dark.

Purple.

Programming inspired.

A little weird.

Something where if somebody lands on it they can probably tell within five seconds that I didn't download a Bootstrap template and change the name.

That meant I immediately started trying to do things I didn't know how to do.

Which has been good.

And painful.

Mostly good.

My Current Relationship With CSS

CSS has taught me that knowing a property exists and understanding the layout system are two completely different things.

For example: 

margin-left: 100px;

Easy.

Move thing right.

Except sometimes it doesn't.

Or it does, but now something else moved.

Or it works perfectly at 100% zoom and then you zoom out and your website looks like somebody dropped all the elements on the floor.

Then you discover Flexbox.

Now you're thinking:

Okay.

I'll just use: 

display: flex;

Problem solved.

Except now you need to understand justify-content, align-items, flex-direction, gap, flex-grow, flex-shrink, and flex-basis.

And eventually you realize the problem wasn't that you needed another CSS property.

The problem was that you didn't understand what the parent element was doing.

That has been a major shift in how I'm thinking about frontend development.

At first I was styling individual objects.

Now I'm starting to think about relationships between objects.

The container.

The child.

The page.

The viewport.

The normal document flow.

How one section affects another.

That's when CSS started making more sense.

Not completely.

CSS still randomly chooses violence sometimes.

But more sense.

Building My Portfolio Before I Feel Ready

I decided pretty early that I don't want to wait until I'm "ready" before building my portfolio.

Because I don't actually know what ready means.

If I wait until I understand HTML perfectly before building anything, then I need to understand CSS.

Then JavaScript.

Then React.

Then backend development.

Then databases.

Then APIs.

Then authentication.

Then deployment.

Then cloud services.

Then probably something else I haven't even heard of yet.

At that rate I'll build my first website when I'm 47.

So instead I'm building it now.

And it looks unfinished.

Because it is.

There are parts of the CSS that are probably terrible.

There are things I'm doing manually that I will probably look at six months from now and wonder what kind of idiot wrote it.

That idiot will be me.

And I'm actually excited for that.

Because if I look at my current code six months from now and think it's great, then I probably didn't improve very much.

My Rule: Make Every Project Slightly Too Hard

This is something I've started doing naturally.

Whenever I learn something, I try adding one thing that I don't know how to do.

If the tutorial builds a converter, I add another conversion.

If the tutorial asks for one input, I'll try allowing unlimited inputs.

If something prints information, I'll try storing it.

If something stores information, I'll try sorting it.

If I build a page, I'll try making the layout more complicated than what I've learned.

Not massively harder.

Just enough that I get stuck.

I'm starting to think getting stuck is probably the most valuable part of learning.

Because when everything works immediately, I'm mostly practicing things I already understand.

When I get stuck, I've found the edge of my knowledge.

That's exactly where I should probably be spending my time.

Google Is Not Cheating

This was another thing I had to get over.

At first I felt like if I had to Google something then I didn't really know programming.

Which is hilarious now.

I would sit there trying to remember some function because I thought looking it up meant I failed.

Eventually I realized professional programmers literally look things up constantly.

The difference isn't whether you use Google.

The difference is what you're Googling.

There's a big difference between searching:

"How do I build a student management system in Python full code"

and searching:

"Python get highest number in list"

The first one outsources the problem.

The second one finds a tool.

That distinction has become extremely important to me.

I want to solve the architecture of the problem myself.

I want to decide:

I need a list here.

I need a loop here.

I need to compare these values.

I need to validate this input.

Then if I don't remember exactly how Python finds the maximum value in a list?

I'm looking that shit up.

There is no trophy for remembering every function.

And Then There Is AI

This is obviously the massive elephant in the room.

I'm learning software development during probably the biggest change the industry has experienced in decades.

AI can write code.

And not just little snippets anymore.

It can build entire components.

It can debug.

It can explain errors.

It can write tests.

It can generate documentation.

It can look at a screenshot and tell you why your CSS is messed up.

It can basically sit beside you while you're programming.

That's incredible.

It's also dangerous if you're learning.

Because AI can remove the exact struggle that teaches you.

The Problem With AI When You're Learning

If I give AI this prompt:

Build me a responsive portfolio website with a sticky navigation bar, animated project cards, dark mode, and mobile responsiveness.

I can get something pretty impressive back.

Then I can paste it into VS Code.

Open the browser.

And look at my beautiful website.

But what did I actually learn?

Almost nothing.

I became a middleman between AI and Chrome.

That's not what I want.

At the same time, completely refusing to use AI seems equally stupid.

I'm trying to become a software developer in a world where software developers use AI.

So pretending it's 2015 doesn't prepare me for the future either.

My solution so far is trying to use AI primarily as a teacher.

Not an employee.

How I'm Trying to Use AI

When I'm stuck, I'm trying not to immediately ask:

"Give me the code."

Instead I'll ask:

"Explain what concept I need to understand to solve this."

That's a massive difference.

For example, if I want the navigation bar on my website to stay visible when the user scrolls, I could ask AI for the CSS.

It would probably give me the answer immediately.

Instead I can say:

Don't give me the answer. Teach me what CSS concepts I need to understand so I can figure out how to make an element stay attached to the viewport while scrolling.

Now suddenly I'm learning about positioning.

Static.

Relative.

Absolute.

Fixed.

Sticky.

Offsets.

Stacking contexts.

z-index.

And then I can try solving the actual problem myself.

That feels like a much healthier way to use AI.

It also means AI can accelerate my learning without replacing the learning.

At least that's the theory.

We'll see.

AI Makes It Very Easy to Lie to Yourself

This is something I think about a lot.

AI makes it possible to build things way beyond your actual skill level.

That's amazing if the goal is just making something.

It's a problem if the goal is learning.

I could probably have AI build the entire portfolio I'm working on right now.

It would probably be better than mine.

Definitely more responsive.

Probably cleaner.

Probably wouldn't have random CSS properties fighting each other.

But then I would have a portfolio showcasing a skill I don't actually have.

That feels pointless.

The entire reason I'm making the portfolio is to document becoming capable of building the things inside the portfolio.

So I'm trying to keep myself honest.

If AI gives me code, I want to understand it.

If I don't understand it, I don't want it in my project.

That's not an absolute rule because sometimes you need to use libraries or tools where you don't understand every single thing happening underneath.

Obviously nobody understands their entire technology stack down to the transistor.

But at my current level, if there's a basic CSS rule in my own stylesheet and I couldn't explain what it does, that's probably a sign I moved too fast.

I Don't Want to Become an AI Dependent Programmer

This is probably one of my biggest concerns.

I don't want to become somebody who can build impressive things as long as ChatGPT is open, but becomes completely useless when something goes wrong.

Because AI-generated code still breaks.

And when it breaks, somebody has to understand it.

That's where I think actual programming knowledge becomes even more important.

If AI writes 300 lines of code and something isn't working, I need to be able to read those 300 lines.

I need to understand the logic.

I need to identify suspicious parts.

I need to test assumptions.

I need to understand the error message.

Otherwise I'm basically just going back to AI saying:

"Didn't work."

Then AI tries something else.

"Still doesn't work."

Then it tries something else.

Eventually maybe it works.

But I didn't engineer anything.

I just rolled the AI slot machine until the program ran.

I don't want that.

My Goal Isn't to Compete With AI

I think this is another thing people get wrong.

I'm not trying to learn how to type code faster than AI.

That battle is already over.

AI wins.

I'm also not trying to memorize more syntax than AI.

AI wins that too.

The skills I think matter are higher level.

Understanding what should be built.

Breaking complicated problems into smaller ones.

Knowing when an answer doesn't make sense.

Understanding systems.

Understanding users.

Making tradeoffs.

Debugging.

Designing architecture.

Knowing enough fundamentals that AI output isn't magic.

And probably most importantly, being able to take an idea from nothing to something.

That's what I want to become good at.

JavaScript Is Coming

At the moment I'm still building up my HTML and CSS understanding.

JavaScript is next.

And JavaScript feels like the point where frontend development becomes actual programming again.

HTML gives the page structure.

CSS makes it look good.

JavaScript makes it do things.

At least that's my extremely simplified understanding right now.

I'm expecting JavaScript to be challenging because I'll be learning programming concepts again while also dealing with the browser.

Variables. Functions. Arrays. Objects. Loops. Conditions. Events. DOM manipulation. Async programming. APIs. Promises.

Probably 900 different ways to write a function for some reason.

I've already seen: 

function thing() {
    }

and: 

const thing = function() {
    }

and: 

const thing = () => {
    }

Why.

I'll find out.

React Is Somewhere in the Distance

After JavaScript I want to learn React.

I'm intentionally not jumping directly into it.

I've seen people recommend learning React immediately because that's what jobs use.

But I don't want React to become another magical layer that I don't understand.

If React changes something on a webpage, I want to understand what it's ultimately doing.

If I'm manipulating state, I want to understand why state exists.

If I'm rendering components, I want to understand what problem components are solving.

I don't want to memorize:

"useState goes here because tutorial man said so."

I want to understand what problem existed before React and why React helps solve it.

Maybe that's slower.

I think it'll make me better in the long run.

Backend Is Where I'm Really Excited

Frontend development is actually becoming more fun than I expected.

But backend development is probably where my brain naturally wants to go.

I like logic.

I like systems.

I like the idea that somebody presses a button on a website and behind that button there could be authentication, databases, APIs, permissions, business logic, caching and a bunch of other systems working together.

That's fascinating to me.

Right now a website feels like what I can see.

Eventually I want to understand everything happening behind what I can see.

I'm planning on learning Node.js eventually because I'm already going to be learning JavaScript.

I also want to continue using Python.

Especially because of AI.

The App I Eventually Want to Build

The biggest project I have in my head right now is a social entertainment platform.

The easiest way to explain it is probably some combination of Letterboxd, IMDb, Reddit, Instagram and Discord.

But I don't literally want to clone all of those and mash them together.

The basic idea is a place centered around movies and television where people can review things, discuss them, follow people, participate in communities, have feeds, create threads, and interact around entertainment.

I also want AI to be built into the actual foundation of the platform instead of being some random chatbot button in the corner.

I don't completely know what that looks like yet.

That's part of why I'm learning.

Maybe AI helps users discover discussions.

Maybe it understands the movies you've watched.

Maybe it can connect conversations across communities.

Maybe it helps moderate spoilers.

Maybe it can summarize massive discussion threads.

Maybe it can recommend things based on extremely specific preferences instead of "you watched an action movie, here is another action movie."

Maybe half of those ideas are terrible.

That's fine.

The important thing is that I have something big enough that I can't currently build it.

That gives me somewhere to go.

Right Now That App Is Way Above My Ability

And that's kind of exciting.

Currently I'm celebrating when I make a webpage element stay where I wanted it to stay.

The application I'm describing would eventually require things like frontend frameworks, backend servers, databases, authentication, user accounts, APIs, search, recommendation systems, image storage, security, moderation, real-time communication, probably WebSockets, cloud infrastructure, testing, deployment, AI APIs, embeddings, retrieval, vector databases maybe, scaling, and a whole pile of stuff I don't understand yet.

If I tried building it today, AI could probably generate a Frankenstein version of it for me.

But I wouldn't understand what I built.

So instead I'm treating that application like the mountain in the distance.

Every smaller project teaches me something I'll eventually need to climb it.

My Portfolio Is Basically My Laboratory

That's what my portfolio website is becoming.

It isn't just somewhere to display projects.

The portfolio itself is a project.

When I learn HTML, it changes.

When I learn CSS, it changes.

When I learn JavaScript, it's going to change dramatically.

When I learn backend development maybe I'll add a real blog system.

Maybe accounts.

Maybe some completely unnecessary feature just because I want to figure out how it works.

I actually like the idea that someone could look through the Git history eventually and see me learning.

Early commits will probably be horrible.

Then slowly things become cleaner.

Maybe the naming improves.

Maybe JavaScript starts appearing.

Then React.

Then APIs.

Instead of hiding the beginner stage, I kind of want the website to document it.

There Is Something Cool About Being Bad at This

That sounds weird.

But there is.

When you're completely new at something, improvement happens extremely fast.

A week ago something can look impossible.

Then suddenly it's normal.

There are already pieces of code that would've confused me before that I can look at now and understand immediately.

That's addictive.

I know eventually the progress probably becomes harder to notice.

The problems get bigger.

The bugs get harder.

The concepts become more abstract.

But right now I can literally feel my brain changing how it looks at problems.

I see a website differently now.

Before I would look at a website and think:

That's a navigation bar.

That's an image.

That's a button.

Now I'm starting to look at it like:

That's probably a container.

Those items are probably Flexbox.

That section probably has a max width.

That background is separate from the content wrapper.

That button probably has hover styles.

That header might be fixed.

There's probably media queries changing that layout on mobile.

I'm still guessing half the time.

But I'm looking differently.

And I think that's progress.

Tutorials Aren't Bad, But Living Inside Them Is

I don't understand why programming discussions online sometimes treat tutorials like they're evil.

Tutorials are incredibly useful.

Somebody who understands a subject organizes it into a logical order and explains it to you.

That's great.

The problem is when the tutorial becomes your permanent environment.

You finish a Python tutorial.

Then instead of building something, you watch "10 Python Projects for Beginners."

Then "Intermediate Python Full Course."

Then "Advanced Python Full Course."

Then "Python OOP Masterclass."

Then six months later you've watched 80 hours of programming and still panic when VS Code opens to an empty file.

I don't want that.

My current philosophy is:

Learn enough that I can start.

Then start.

When I get stuck, learn the next thing.

Then continue.

It's messier.

But it feels more real.

I Also Need to Get Comfortable With Not Knowing Things

Programming has an almost comical amount of information.

Every time I learn one thing, it reveals five more things.

Learn HTML. Cool. Now CSS.

Learn CSS. Cool. Flexbox. Grid. Responsive design. Animations. Accessibility.

Learn JavaScript. Now Node. React. TypeScript. npm. Bundlers. APIs. Databases. SQL. Git. Docker. Cloud. Testing. Security. CI/CD. Linux.

And I'm sure somebody reading that list is already thinking:

"You forgot ______."

Yes.

Exactly.

That's the point.

There is always another thing.

So I'm slowly accepting that becoming a software engineer doesn't mean reaching a point where I finally "know programming."

That point doesn't exist.

Maybe the real skill is becoming comfortable entering a problem where you don't know everything.

You know enough to start.

Then you research.

Then you experiment.

Then you understand a little more.

Then you keep going.

Git Was Another Weird Mental Shift

Version control seemed incredibly boring when I first heard about it.

It's basically a system for keeping track of changes to code.

Okay.

Cool.

Not exactly the thing that makes somebody want to become a programmer.

But once I started actually building things, I understood why it matters.

Code changes constantly.

And sometimes you improve it.

Sometimes you destroy it.

There is something very comforting about knowing you can experiment without permanently murdering the version that worked.

Git also introduces another way of thinking.

Changes become intentional.

Instead of randomly editing 19 files and hoping everything survives, you can make a specific change and record what that change was.

I'm still early with Git.

But I can already tell it's one of those tools that probably becomes invisible once you've used it long enough.

I Have Started Reading Error Messages

This deserves its own section because beginner me apparently thought error messages were decorative.

Program crashes.

Red text appears.

My response:

"Oh no."

Then immediately Google the entire error.

Now I'm actually trying to read it.

Which, shockingly, helps.

Python will literally tell me what line caused the problem.

It will often tell me what type of error happened.

Sometimes the exact message basically explains the problem.

I still don't understand every error.

Not even close.

But now the error itself is the beginning of debugging instead of just evidence that I failed.

That's a big difference.

I Think I'm Starting to Understand What "Thinking Like a Programmer" Means

People say this constantly.

"Learn to think like a programmer."

It sounds like motivational nonsense when you don't know what it means.

I think I'm beginning to understand it.

It's not some special genius brain.

It's basically being annoyingly specific.

Normal person:

"I want a program that stores student grades."

Programmer:

Okay.

What counts as a student?

How does the user enter a student?

Can two students have the same name?

What type is the grade?

Can grades have decimals?

What's the minimum?

What's the maximum?

How does the user indicate they're finished?

What happens if they enter invalid information?

Where is the information stored?

Does it need to persist after the program closes?

How do we calculate the average?

What happens if there are zero students?

What happens if somebody types letters instead of a grade?

Normal person:

Bro I just wanted the grades stored.

But computers are incredibly literal.

So somebody has to think through all of that.

That's the job.

The Computer Doesn't Know What You Meant

This is probably the funniest lesson in programming.

The computer does not care what you meant.

At all.

You can stare at your code and say:

"YOU KNOW WHAT I'M TRYING TO DO."

No.

It doesn't.

It knows exactly what you told it to do.

Nothing more.

If your instructions accidentally say:

"Keep asking this question forever."

Congratulations.

The computer will ask that question until the heat death of the universe.

That's actually made me appreciate programming more.

Software feels intelligent when you're using it.

But underneath, somebody had to account for an insane amount of behavior.

Every button.

Every edge case.

Every invalid input.

Every error state.

Every weird user doing something nobody expected.

And users will always do something nobody expected.

I know this because I am usually that user.

My Current Learning Plan

My plan is probably going to change.

Actually, I guarantee it will.

But right now the general direction is:

Python fundamentals → HTML → CSS → JavaScript → deeper JavaScript → Node.js → databases → React → full-stack projects → AI integration

There will obviously be other things mixed in.

Git. GitHub. Command line. APIs. SQL. Deployment. Testing. Security basics. Data structures. Algorithms. Computer science fundamentals.

I don't think learning needs to happen in a perfectly straight line.

Actually I think trying to create the perfect learning order can become another form of procrastination.

Eventually you have to write code.

My Goal for the Next Few Months

I want to get to a point where I'm not scared of blank files.

That's probably the simplest way I can explain it.

Give me a problem.

I don't need to immediately know the solution.

But I want to know how to begin.

I want to be able to say:

Okay.

First I need this.

Then probably this.

I don't know how to do this third part, so I'll research it.

Then I'll test it.

Then I'll continue.

That seems much more valuable than memorizing every method in Python or JavaScript.

I want to build enough projects that problem solving starts becoming natural.

The Job Question

Obviously I want this to eventually become a career.

I know the software job market isn't exactly the easiest thing in the world right now.

Especially for junior developers.

AI has also created this weird situation where the definition of "junior developer" itself might be changing.

If AI can generate boilerplate code instantly, then companies probably won't care as much that you can manually type boilerplate code.

That means the standard might become higher.

That is intimidating.

But it's also why I don't want to optimize my learning around passing some arbitrary checklist.

I want to actually become useful.

If I can build things, debug things, understand existing code, communicate what I'm doing, learn unfamiliar technologies, use AI effectively, and prove all of that through projects, then I think I give myself a real chance.

Maybe it takes six months.

Maybe twelve.

Maybe longer.

I don't know.

I'm trying not to obsess over the exact timeline.

I Know I'm Going to Write Bad Code

A lot of it.

Probably thousands of lines.

That's unavoidable.

You can't somehow skip being a beginner.

And AI creates this temptation to skip it because AI can instantly show you what "good" code looks like.

But reading good code isn't the same as developing the instincts that produce good code.

I need to make the stupid version first.

Then discover why it's stupid.

Then fix it.

That's where the lesson lives.

If I write 30 lines and later learn it could've been five?

Good.

Now I'll understand why those five lines are better.

If AI just gave me the five lines immediately, I might know the solution but not understand the improvement.

Sometimes My Code Is Embarrassing

Even already.

I'll solve something using five if statements and then discover Python has a built-in function that does the entire thing.

Or I'll create variables I didn't need.

Or repeat code.

Or make names that made perfect sense at 2 AM and absolutely no sense the next morning.

But I'm trying not to clean up the evidence too much.

Because that's literally what learning looks like.

Nobody begins writing beautiful production code.

At least I hope not because that would make me feel significantly worse.

I Want to Document Everything

That's one reason this blog exists.

I don't want to only document the successful projects.

I want to document the confusion too.

The bugs.

The things I misunderstood.

The projects that went nowhere.

The terrible first versions.

The moments something finally clicked.

Because I think if I actually stick with this, eventually I'll be able to come back here and see the distance.

Maybe a year from now I'll read this post and laugh at what I thought was difficult.

I hope so.

That's kind of the goal.

The AI Part of This Journey Is Going to Be Interesting

I genuinely don't know what software engineering looks like five years from now.

I don't think anybody actually does.

People have predictions.

Some think AI replaces most programmers.

Some think it creates more software jobs.

Some think software engineers become more like architects directing AI systems.

Some think the entire process of building software changes.

Probably some combination of all of it happens.

But one thing seems obvious.

AI isn't going away.

So I would rather learn alongside it.

I want to understand programming fundamentals while also becoming extremely good at using AI tools.

Not one or the other.

Both.

I think the dangerous position is being completely dependent on AI without understanding software.

But I also think there's going to be another dangerous position:

Being technically excellent but refusing to use tools that make you dramatically faster.

I don't want either.

What I Want AI to Become for Me

Eventually I want AI to feel like another development tool.

Like Git.

Or Google.

Or documentation.

Something I can use intentionally.

Maybe I ask it to explain unfamiliar code.

Maybe I use it to brainstorm architecture.

Maybe it writes repetitive tests.

Maybe it reviews my code.

Maybe it helps me find edge cases.

Maybe it creates a first draft of something I've already designed.

Maybe I disagree with it.

That's important too.

I want to reach the point where I can look at AI-generated code and say:

"No. That's a terrible way to do this."

Right now AI knows dramatically more about programming than I do.

So most of the time I can't confidently do that.

Someday I want to.

That will probably be one of the clearest signs I've improved.

A Weird Thing Has Already Happened

The more I learn programming, the more I realize how little I know.

Which sounds depressing.

It actually isn't.

At the very beginning I didn't know enough to understand the size of the field.

Programming was just:

"People write code and make apps."

Now every layer I learn reveals another layer underneath it.

A website isn't just a website.

There's HTML.

CSS.

JavaScript.

Frameworks.

HTTP.

Servers.

Databases.

DNS.

Caching.

Authentication.

CDNs.

Browsers.

Networking.

Operating systems.

And eventually electricity doing witchcraft inside silicon.

I'm obviously not going to master every layer.

Nobody does.

But I like knowing that the rabbit hole keeps going.

There Is Also a Creative Side I Didn't Expect

This surprised me.

Programming always looked extremely technical from the outside.

And obviously it is.

But building software feels surprisingly creative.

There are hundreds of ways to solve the same problem.

There are design decisions.

Architecture decisions.

User experience decisions.

Naming decisions.

Tradeoffs.

You're basically creating a little world with rules.

Especially with web development.

You start with an empty file.

Literally nothing.

Then slowly a thing exists.

A header.

A section.

A button.

An interaction.

A database.

A user.

A community.

That's really cool.

It's one of the reasons I think programming fits me more than I expected.

There are CSS properties I've used and then immediately forgotten.

I am very much still a beginner.

But I'm a better beginner than I was before.

And tomorrow hopefully I'll be a slightly better beginner again.

The Main Thing I'm Proud of So Far

It's not any specific project.

It's that I'm starting to attempt things before knowing how to do them.

That is probably the biggest difference.

Before, if I didn't know how to build something, I would think:

"I need to learn how to build this."

Now I'm starting to think:

"Let me try."

Those sound almost identical.

They're not.

The first one usually leads to another tutorial.

The second one leads to code.

Usually broken code.

But code.
